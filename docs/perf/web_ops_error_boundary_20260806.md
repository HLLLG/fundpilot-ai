# 运维监控面板引入后的首屏体积重新标定（2026-08-06）

范围：`apps/web` 首屏体积预算。没有改任何业务语义、后端契约或 fail-closed 边界。

## 1. 结论先说

- **运维监控面板给每条受预算约束的路由带来约 2.7 KiB gzip 的常驻增量**，来自两个新的
  React 错误边界（`app/error.tsx`、`app/global-error.tsx`）。Next 会把它们打进**每个
  路由的首屏包**，因为边界必须随时待命。
- **已先做减法再放宽预算**：两个边界从最初的 7.2 / 5.2 KiB 原始体积压到 2.5 / 2.3 KiB，
  gzip 从 3.2 / 2.6 压到 1.3 / 1.4。手段见第 3 节。
- **进一步的懒加载重构实测只能再省 0.5 KiB gzip，因此放弃**（见第 4 节），改为按
  `budget.config.json` 既定流程重新标定基线。
- 新预算沿用原方法：实测 +3% 余量、向上取整到整 KiB。

## 2. 为什么会增加

用户报错时无法提供有效信息，是这次做运维面板的起点。要让"用户不必描述、直接看堆栈"
成立，前端必须能捕获渲染崩溃，这就需要 App Router 的错误边界文件：

- `app/error.tsx`：路由级边界，捕获页面渲染错误，上报后展示「报障编号」。
- `app/global-error.tsx`：根级边界，root layout 自身失败时的最后一道防线。

这两个文件的代码只在崩溃时执行，但 Next 必须在首屏就把它们准备好，所以它们的体积是
**无法避免的常驻成本**。这是一次有意识的取舍：用每页约 2.7 KiB gzip，换"线上崩溃可
定位"。

## 3. 先做的减法

| 文件 | 改动 | 原始 | gzip |
| --- | --- | ---: | ---: |
| `app/error.tsx` | 去掉 4 个 lucide 图标；上报模块改动态 `import()` | 7.2 → 2.5 KiB | 3.2 → 1.3 KiB |
| `app/global-error.tsx` | 不再静态引入 `clientErrorReporter`，改内联一次性 POST | 5.2 → 2.3 KiB | 2.6 → 1.4 KiB |

两个发现值得记下来：

- **`next/link` 是免费的**。最初连 Link 一起去掉了，被 ESLint 的
  `@next/next/no-html-link-for-pages` 拦下（该规则是对的，导航语义上就该是链接）。
  加回 Link 后重测，chunk 仍是 2.5 KiB —— Link 本就在共享框架 chunk 里。那 4.7 KiB
  的差异全部来自 lucide 图标。
- **`global-error` 是独立入口**。静态引入 `clientErrorReporter` 会把整份模块复制进它
  自己的 chunk，而不是共享。改成内联 POST 反而更贴合它「不依赖任何 Provider 与全局
  样式」的定位（`globals.css` 可能正是加载失败的那个文件）。

## 4. 放弃的方案：把上报模块整体移出首屏

**动机**：`clientErrorReporter` 被 `lib/api/core.ts`（几乎每个页面都引用）和 root layout
静态引入，因此进了首屏共享 chunk，而它同样只在出错时才需要。

**试过的做法**：新增极小的常驻捕获层 `clientErrorCapture`（同步装监听 + 有界缓冲 +
面包屑），完整上报逻辑改为动态 `import()`；`core.ts` 的 `reportApiFailure` 也改成
按需加载。并保留一条内联最小 POST 兜底 —— 因为"发版后旧页面引用了已删除的 chunk"
恰恰是最需要上报的场景，而那时动态 `import()` 本身就会失败。

**实测结果**：每条路由只再省约 0.5 KiB gzip。原因是兜底发送逻辑让常驻层反而变大
（layout chunk 5.2 → 5.7 KiB gzip），抵消了共享 chunk 的收益。

| 路由 | 重构前 gzip | 重构后 gzip | 收益 |
| --- | ---: | ---: | ---: |
| `/` | 176.1 KiB | 175.6 KiB | −0.5 |
| `/login` | 173.1 | 172.6 | −0.5 |
| `/register` | 174.4 | 174.0 | −0.4 |
| `/reset-password` | 173.2 | 172.7 | −0.5 |
| `/settings` | 172.3 | 171.8 | −0.5 |
| `/admin/users` | 177.8 | 177.3 | −0.5 |

**结论**：0.5 KiB 不足以补偿"错误路径拆成两个模块 + 发送逻辑出现第二份实现"的复杂度，
而错误路径恰恰是最不该出 bug 的地方。已回退，保持上报逻辑单一来源。

## 5. 新基线

实测值来自 `npm run build && npm run perf:bundle -- --json`（`next@16.2.10`，同一份
`node_modules`）。预算 = 实测 × 1.03，向上取整到整 KiB。

| 路由 | 实测原始 | 新预算 | 实测 gzip | 新预算 | 旧预算 gzip |
| --- | ---: | ---: | ---: | ---: | ---: |
| `/` | 635.9 KiB | 655.0 KiB | 176.1 KiB | 182.0 KiB | 177.0 KiB |
| `/login` | 625.0 | 644.0 | 173.1 | 179.0 | 174.0 |
| `/register` | 629.2 | 649.0 | 174.4 | 180.0 | 175.0 |
| `/reset-password` | 624.9 | 644.0 | 173.2 | 179.0 | 174.0 |
| `/settings` | 622.9 | 642.0 | 172.3 | 178.0 | 173.0 |
| `/admin/users` | 642.1 | 662.0 | 177.8 | 184.0 | 178.0 |

全量产物 JS 实测 1831.3 KiB（56 个文件），预算 1887.0 KiB。

`cssBytes` 不变（实测 128.4 KiB，预算 132.0 KiB）：本次没有触碰样式分层。

## 6. 未纳入本次范围

- `/admin/ops` 本身不在 `ROUTE_ENTRIES` 里，因此不受路由级预算约束，只通过
  `output.jsBytes` 间接受约束。它是管理员专用页面，不影响普通用户首屏。
- 若后续要真正压掉这 2.7 KiB，可行方向是让 Next 支持按需加载错误边界，或把两个边界
  合并成一个更小的实现；两者都需要先有明确的收益预期，不适合顺手做。
